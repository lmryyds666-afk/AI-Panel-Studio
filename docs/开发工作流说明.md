## 一、项目标准分层开发完整流程

本项目严格遵循 **SDD → DDD → TDD → E2E** 四阶段推进范式，每个阶段聚焦单一模块，禁止一次性生成全项目代码。实际执行时间线如下：

### 阶段 1：SDD 数据建模与契约定义

| 步骤 | 产出 | 工具 |
|:--|:--|:--|
| 1.1 数据建模 | `prisma/schema.prisma`（4 实体：Discussion / Guest / Speech / ConsensusRecord） | Prisma 7 + SQLite |
| 1.2 ER 图绘制 | `docs/ER图.md`（Mermaid 实体关系图 + 关系表） | Mermaid |
| 1.3 API 契约 | `docs/API规范.md`（6 REST 端点 + 5 WebSocket 事件完整契约） | Markdown |

**关键决策**：先锁定数据结构和接口契约，后续所有层均以此为唯一真源，避免返工。

### 阶段 2：DDD 页面设计

| 步骤 | 产出 | 说明 |
|:--|:--|:--|
| 2.1 PRD 需求梳理 | 用户故事 + 功能边界 | 明确三大页面（首页/配置/演播厅）交互逻辑 |
| 2.2 组件树拆分 | 18 组件树 + 响应式断点策略 | `docs/PRD页面设计.md` |
| 2.3 基础页面开发 | React 19 + Vite 6 + Tailwind CSS v4 三页面骨架 | 纯静态布局，不含业务逻辑 |

### 阶段 3：TDD 后端开发

严格遵循"先写测试→确认失败→最小实现→确认通过→重构"铁律：

| 步骤 | 产出 | 用例数 |
|:--|:--|:--|
| 3.1 中间件测试 + 实现 | validate / error-handler / logger | 21 |
| 3.2 路由 + 控制器测试 | 6 REST 端点 + 状态机校验 + 错误场景 | 27 |
| 3.3 嘉宾生成服务 | prompt 构建 / JSON 提取容错 / Zod 校验 / 数据库写入 | 15 |
| 3.4 AI 发言调度引擎 | 上下文隔离 / 多行为调度 / 状态机 / WS 广播 | 25 |
| 3.5 共识/分歧提炼 | 增量提炼 / 限流 / 重试 / 多讨论隔离 | 15 |

### 阶段 4：基础业务底座

## 二、AI 协同开发典型问题与解决方案

### 问题 1：多讨论数据隔离失效，发言与共识跨房间串流

**现象**：同时运行两场讨论时，讨论 A 的发言错误出现在讨论 B 的 Transcript 面板中，共识/分歧记录也发生交叉。

**根因分析**：
1. WebSocket 广播未按 `discussionId` 划分独立房间——服务端向所有连接的客户端广播了所有讨论的事件
2. `SpeechScheduler` 和 `ConsensusExtractor` 的内存上下文未绑定单场讨论标识，不同讨论共享了同一份状态

**解决方案**：
- Socket.IO 服务端按 `discussion:${discussionId}` 创建命名房间，客户端连接时通过 `handshake.query.discussionId` 自动加入对应房间，广播使用 `io.to(room).emit()` 天然隔离
- 调度器使用 `Map<discussionId, DiscussionContext>` 按讨论 ID 存储独立上下文
- 共识提炼器同样维护 `Map<discussionId, ExtractionState>` 按讨论隔离
- 所有数据库查询强制携带 `WHERE discussionId` 条件
- 单元测试增加多房间并发校验用例（同时启动 2 场讨论，验证每场只收到自身事件）

### 问题 2：大模型输出自由文本，结构化数据解析失败

**现象**：AI 返回的发言决策和共识提炼中夹带说明文字、markdown 包裹、尾逗号等非标准 JSON 格式，前端解析报错，页面白屏。

**根因分析**：
1. Prompt 仅描述了输出格式要求，未强制约束 JSON Schema 字段类型
2. 缺少对 AI 输出的容错清洗逻辑——直接 `JSON.parse()` 对非法格式零容忍
3. 没有 Zod 结构校验作为最后防线，非法字段穿透到数据库

**解决方案**：
- Prompt 中明确指定完整 JSON Schema（含字段名、类型、约束），使用 ` ```json ``` ` 代码块模板引导 AI 输出
- 实现 `extractJSON()` 容错提取函数：优先匹配 markdown 代码块 → 括号配对扫描定位 JSON 对象 → `cleanJSON()` 移除注释与尾逗号
- 所有 AI 输出必经 Zod `safeParse()` 校验，校验失败抛出详细错误信息（含字段路径 + 期望类型 + 实际内容前 500 字符）
- 发音调度器和共识提炼器各自定义独立的 Zod Schema，不通用的字段不共享 Schema

### 问题 3：前端全屏纯黑工业风格，视觉体验生硬压抑

**现象**：页面大面积使用 `bg-slate-900` / `bg-gray-950` 纯黑底色，配合深色边框与高饱和蓝色按钮，整体氛围机械冰冷，缺乏亲和力。

**根因分析**：
1. 仅使用纯色深色背景，无分层视觉效果
2. 无自然元素点缀，AI 工具感过重
3. 卡片/面板背景不透明度低，无法形成视觉纵深

**解决方案**：
- 底层叠加长白山天池半透明自然风光固定背景（`background-attachment: fixed`）
- 全局增加半透明深色色调遮罩层（`rgba(15, 23, 42, 0.55)`），确保文字可读
- 所有卡片/面板/弹窗使用玻璃拟态（Glass Morphism）：`backdrop-filter: blur()` + 半透背景 + 柔和边框 + 多层阴影
- 弱化按钮和标签色彩饱和度（`indigo-600→500/85`、`green-600→emerald-500/85`、`red-600→rose-500/85`）
- 新增全局页脚（项目名 + 作者 + 联系方式）+ 演播厅导航栏返回首页按钮
- 移动端适配（`@media (max-width: 640px)` 缩小浮空按钮边距与字号）

## 三、模块化 AI 协同开发设计思路

### 1. 拆分原则

单次提示词仅下发一个独立模块，禁止一次性生成全项目代码。每个模块有明确的输入（上游接口契约）和输出（可独立验证的功能单元），降低模块间耦合，便于问题快速定位与回滚。

### 2. 分层优势

先完成底层数据模型与 API 接口底座，再向上构建实时通信与 AI 核心业务，最后迭代前端视觉与调试工具。底层稳定后，上层业务无需因底层变更而反复修改——例如 Prisma Schema 锁定后，所有 Controller 和 Service 只需关注自身业务逻辑，数据访问模式不再变化。

### 3. 交付规范

每完成一个模块，归档该模块对应的开发 Prompt 与开发意图说明，留存完整的开发过程证据链。这份记录既是实习交付物的硬性要求，也是后续 AI 协同开发时可复用的上下文资产——新的 AI 会话可通过 Prompt 记录快速理解模块设计意图。

### 4. 测试兜底

每个后端模块编写配套单元测试（Jest），前端配套 E2E 自动化用例（Cypress）。测试侧重点因模块而异：

- **中间件/路由**：校验规则 + 错误码 + 边界值
- **AI 服务**：Mock AI 响应 + Zod 校验 + 业务规则验证
- **WebSocket**：房间隔离 + 事件信封格式 + 多客户端并发
- **前端 E2E**：全流程关键路径（创建→生成→确认→演播厅→结束）

测试先行（TDD）确保功能在首次实现时即经过验证，后续迭代修改有安全网兜底，避免回归。
