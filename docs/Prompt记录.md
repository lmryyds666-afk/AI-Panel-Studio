# AI 圆桌讨论 Web App：核心 Prompt 记录文档

> 本文档记录使用 Claude Code（接入 DeepSeek V4 Pro 模型）进行 AI Panel Studio 项目开发的核心 Prompt。
> 每个 Prompt 均标注对应开发范式阶段，并附意图说明、遇到的挑战及引导 AI 修正的方法。

---

## 项目背景 Prompt（第 0 轮：全局上下文锚定）

```
你是 Claude Code，正在协助我完成「AI Panel Studio」AI 圆桌讨论 Web App 的开发作业。
以下是完整项目需求文档，你仅作为全局参考，后续我会分多次下发细分任务，
每次只完成单一模块，禁止一次性生成完整项目代码。

[粘贴 D:\卓面\项目要求.md 全文]
```

**记录说明**

- **意图**：先让 AI 建立完整的产品语境，避免后续模块开发时出现需求理解偏差；同时明确「禁止一键生成」的红线规则，为后续所有 Prompt 设定行为边界。
- **挑战**：大模型容易在首次对话就试图「帮忙生成项目骨架」，必须在第 0 轮就把「分阶段、单模块」的协作模式写死。
- **修正方法**：在 Prompt 末尾增加「每次只完成单一模块，禁止一次性生成完整项目代码」的强约束；后续每轮 Prompt 开头重复标注当前阶段，形成范式锚定。

## Prompt 1【SDD 阶段｜任务：SQLite 数据建模】

```
/superpowers:spec-driven-development

【SDD阶段｜单一任务：仅完成SQLite数据建模】
基于 AI Panel Studio AI 圆桌 Web App 需求，仅输出两部分内容：
1. Mermaid 完整 ER 图代码（erDiagram 语法）；
2. Prisma Schema 模型代码（datasource 使用 SQLite）。

约束规则：
1. 实体包含 Discussion、Guest、Speech、ConsensusRecord，
   所有数据通过 discussion_id 隔离多场讨论；
2. Guest 字段包含：姓名、职业、Title、立场、专属颜色（HEX）、
   运行状态（IDLE / PREPARING / SPEAKING）；
3. ConsensusRecord 区分 CONSENSUS、DIVERGENCE 两种类型；
4. Speech 包含 speechType 字段（OPENING / FOLLOW_UP / BRIDGING /
   ANSWER / SUPPLEMENT / COUNTER / SUMMARY）；
5. 禁止输出接口代码、前端代码、业务逻辑，
   只输出数据建模相关内容。
```

**记录说明**

- **意图**：先锁死底层数据结构，确保后续开发不会出现字段缺失、多讨论数据串扰的问题；SDD 阶段的核心产出是「稳定的数据契约」，而非功能代码。
- **挑战**：AI 容易在输出 ER 图后「顺带」生成 Prisma Client 调用代码，或主动补充 API 接口设计，偏离「单一任务」约束。
- **修正方法**：在约束规则第 5 条明确禁止非建模内容；通过「仅输出两部分内容」的正面表述 + 「禁止输出」的负向表述双重约束，引导 AI 聚焦。

## Prompt 2【SDD 阶段｜任务：前后端 API + WebSocket 契约文档】

```
/superpowers:spec-driven-development

【SDD阶段｜单一任务：仅输出API与实时事件文档】
基于上一轮生成的 Prisma 数据模型，只输出接口规范文档，
禁止写任何接口实现代码。

要求：
1. 输出 RESTful 接口清单（含请求/响应 JSON 示例）：
   - POST   /api/discussions       创建讨论
   - GET    /api/discussions       讨论列表
   - POST   /api/discussions/:id/guests 生成嘉宾
   - POST   /api/discussions/:id/end    结束讨论
2. 输出 WebSocket 实时事件定义（含事件 payload 示例）：
   - guest:status   嘉宾状态更新
   - speech:new     新发言推送
   - consensus:update   共识/分歧刷新
   - discussion:summary  总结推送
3. 所有接口/事件必须携带 discussion_id，保证多讨论数据隔离；
4. 只输出 markdown 格式文档，不生成前端、后端业务代码。
```

**记录说明**

- **意图**：在写任何前后端代码之前，先把「数据如何流动」定义清楚；这份契约文档后续直接指导 TDD 阶段的 Service 实现和 DDD 阶段的前端状态设计。
- **挑战**：AI 倾向于在定义事件后「顺手」生成 WebSocket 服务端代码，或给出前端 `useWebSocket` Hook 实现，违反「单一任务」原则。
- **修正方法**：在第 4 条约束中再次强调「只输出文档」；同时在 Prompt 开头重复标注 `【SDD阶段｜单一任务】`，利用阶段标签帮助 AI 维持上下文聚焦。

## Prompt 3【DDD 阶段｜任务：演播厅页面布局与组件拆分设计】

```
【DDD阶段｜任务：前端页面与组件拆分设计】
需求：AI 圆桌演播厅中文响应式页面，分三大页面：
首页讨论列表、嘉宾配置页、演播厅主页面。

演播厅硬性布局要求（参照腾讯会议/演播厅视觉风格）：
1. 顶部区域：讨论标题 + 结束按钮；
2. 左侧独立滚动区域（约 280px）：
   多嘉宾状态小卡片，显示角色、状态、专属颜色、思考摘要；
3. 中间独立滚动（flex:1）：
   发言记录 Transcript，用与专家一致的色块区分发言人；
4. 右侧独立滚动（约 320px）：
   实时共识/分歧面板，含 CONSENSUS / DIVERGENCE 标签；
5. 全页面分区域独立滚动（各区域 overflow-y:auto），
   适配超宽屏 / 桌面 / 移动端窄屏（移动端上下堆叠）。

输出要求：
- Mermaid 页面布局示意图（3 个页面的页面流）；
- 全部组件拆分清单（组件名、职责、props 入参、状态来源）；
- 每个组件的视觉规范（尺寸、颜色、字体、交互状态）；
- 禁止直接输出完整可运行前端页面代码，仅输出设计文档。
```

**记录说明**

- **意图**：DDD 阶段的核心是用「视觉设计」驱动后续前端实现，而不是让 AI 直接写 React 组件；先产出高保真设计文档，后续实现阶段只需「按图施工」。
- **挑战**：AI 极度倾向于直接生成完整的 React `+ Tailwind` 页面代码（因为它「看起来更有用」），必须通过强约束阻断这种行为。
- **修正方法**：在输出要求第 4 条明确「禁止直接输出完整可运行前端页面代码」；同时在布局要求中增加具体数值（280px、320px、flex:1），让 AI 输出的设计文档具备可直接实现的精确度，减少后续模糊空间。

## Prompt 4【TDD 阶段｜任务：嘉宾生成 Service + Jest 单元测试】

```
【TDD阶段｜单一任务：嘉宾生成逻辑+Jest单元测试】
依赖 SDD 阶段 Prisma 模型与 API 契约，接入 DeepSeek V4 Pro。

执行顺序（严格遵循 TDD 红-绿-重构循环）：
1. 【先写测试】编写完整 Jest 单元测试文件，
   覆盖以下用例：
   - 默认 4 人嘉宾生成（1 主持 + 3 专家）
   - 嘉宾立场不重复（同一讨论内）
   - 嘉宾专属颜色不重复（HEX 值去重）
   - 多讨论隔离（不同 discussionId 生成独立嘉宾集）
   - 大模型返回 JSON 格式异常时的降级处理
2. 【再实现】实现 guest-generation.service.ts，
   包含：调用 DeepSeek V4 Pro 的 prompt 模板、
   JSON 结构校验（zod 或手动校验）、
   立场/颜色去重逻辑；
3. 【只做嘉宾生成】不包含演播厅发言调度、实时推送逻辑；
4. 输出：测试文件完整代码 + Service 实现代码 + Prisma Client 封装（prisma.ts）。

技术约束：
- 使用 prisma/mongodb-adapter 连接 SQLite；
- DeepSeek API Key 从 process.env.DEEPSEEK_API_KEY 读取，
  禁止硬编码；
- 所有 AI 调用必须有超时与重试机制。
```

**记录说明**

- **意图**：TDD 阶段的核心是「先断言后实现」，用测试用例强制大模型返回的数据结构稳定；嘉宾生成是依赖 AI 最多的模块，必须用测试套住 AI 的输出幻觉。
- **挑战**：大模型返回 JSON 格式容易错乱（多出标点、缺少字段、中文编码问题），且 AI 写作代码时容易「跳过测试直接实现」，违反 TDD 流程。
- **修正方法**：在 Prompt 中明确标注「执行顺序（严格遵循 TDD 红-绿-重构循环）」，并要求「先写测试」作为第 1 步；在测试覆盖用例中 explicit 列出 JSON 格式异常的降级处理，引导 AI 在实现时主动加入校验逻辑。

## Prompt 5【E2E 阶段｜任务：Cypress 端到端测试脚本】

```
【E2E阶段｜单一任务：全流程端到端测试脚本】
基于已完成的后端 Service 与前端组件设计，编写 Cypress E2E 测试，
覆盖完整用户操作链路：

测试场景（按顺序执行）：
1. 首页讨论列表渲染（无讨论时显示空状态）
2. 新建讨论 → 填写话题与专家人数 → 提交
3. 嘉宾生成结果展示（姓名、职业、颜色标识正确渲染）
4. 进入演播厅 → 验证 Transcript 区域独立滚动
5. 模拟 WebSocket 推送 → 验证嘉宾状态小窗实时更新
6. 验证共识/分歧面板数据隔离（两个不同 discussion_id
   的测试数据互不干扰）
7. 结束讨论 → 验证总结内容正确展示（无 JSON 原文泄漏）

要求：
- 使用 cy.intercept() 模拟后端 API 响应，
  使用 cy.stub() 模拟 WebSocket 事件；
- 测试数据使用 fixtures/ 目录下的 JSON 文件；
- 每个测试文件必须以 `describe('...', () => { ... })`
  规范组织；
- 仅输出 Cypress 测试代码与 fixtures 文件，
  不修改前后端业务代码。
```

**记录说明**

- **意图**：E2E 阶段的目标是验证「整套系统能否端到端跑通」，重点检查多讨论隔离是否真正生效、实时推送是否丢失；测试脚本本身也是「可运行的交付物」，展示对系统质量保障的重视。
- **挑战**：E2E 测试容易写成「依赖真实后端」的集成测试，导致 CI 环境无法运行；必须通过 `cy.intercept()` 完全模拟后端，保证测试的独立性与可重复性。
- **修正方法**：在要求第 1 条明确使用 `cy.intercept()` 模拟后端 API，避免 AI 生成依赖真实服务器的测试代码；增加「多讨论数据隔离」作为独立测试点（第 6 条），呼应项目要求中的核心考察点。

## 附录：Prompt 设计经验总结

### 有效模式

1. **阶段标签前置**：每个 Prompt 开头用 `【SDD阶段｜单一任务：...】` 格式，帮助 AI 维持上下文聚焦，减少跨阶段内容溢出。
2. **正面 + 负向双重约束**：既说明「要输出什么」，也说明「不要输出什么」；经验表明负向约束对抑制 AI 「过度帮助」特别有效。
3. **数值化布局要求**：在 DDD 阶段给出具体像素值（280px、320px），让设计文档具备可直接实现的精确度。
4. **TDD 执行顺序显式标注**：用「1.【先写测试】2.【再实现】」明确步骤，抑制 AI 跳过测试直接写实现的倾向。

### 踩过的坑

1. **AI 容易「顺带生成」额外代码**：尤其在 SDD 阶段，生成 ER 图后容易主动补充 Prisma Client 调用示例；解决方法是增加「禁止输出」约束，并在每轮 Prompt 重复阶段标签。
2. **大模型返回 JSON 格式不稳定**：在 TDD 阶段必须通过测试用例 + 手动 JSON 校验双重保障；不能依赖 AI 模型的「格式遵守承诺」。
3. **E2E 测试依赖真实后端**：必须通过 `cy.intercept()` 完全模拟，否则测试在 CI 环境无法运行；这一点要在 Prompt 中显式要求。
